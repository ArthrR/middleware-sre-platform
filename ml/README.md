# ml/

Offline training jobs — not long-running services, so they live outside `docker-compose/apps/`. Run against the `mlflow` service from the `ai` compose profile.

## anomaly-detection/

An `IsolationForest` that flags anomalous SRE metrics (`cpu_usage`, `request_latency_ms`, `error_rate`) — the same shape of data this lab's own Prometheus stack produces. Chosen over a generic tutorial dataset (iris/titanic) because it ties the MLOps demo back to the SRE side of this lab: anomaly detection on infra metrics is a real, recognizable AIOps use case.

### Run it

```bash
cd docker-compose
docker compose --profile ai up -d mlflow

cd ../ml/anomaly-detection
pip install -r requirements.txt
python train.py --tracking-uri http://localhost:5000
```

Open http://localhost:5000 to see the run: logged params (`n_estimators`, `contamination`), metrics (`anomalies_detected`, `anomaly_rate`, and `precision`/`recall`/`f1` since the sample dataset ships with synthetic ground-truth labels), a plot artifact, and a registered model version under `prometheus-anomaly-detector`.

### Data

- `data/sample_metrics.csv` — synthetic, generated by `generate_sample_data.py` (stdlib-only, seeded, reproducible). Documented as synthetic; the `label` column is ground truth for evaluating the model, not something real Prometheus data would have.
- `export_prometheus_metrics.py` — optional "live" data source. Pulls real data from this lab's own running Prometheus via the range-query API (`node_cpu_seconds_total`, `ai_gateway_inference_duration_seconds`, `ai_gateway_errors_total`) into the same CSV shape (minus `label`, since there's no ground truth for real data):
  ```bash
  python export_prometheus_metrics.py --hours 2 --out data/live_metrics.csv
  python train.py --data data/live_metrics.csv
  ```

### Data versioning (DVC)

`sample_metrics.csv` is tracked with DVC rather than committed as a raw file — `git` tracks the small `.dvc` pointer (`data/sample_metrics.csv.dvc`), DVC tracks the actual bytes.

The remote is a **local filesystem directory outside the repo** (`../ai-platform-lab-dvc-remote`, configured in `.dvc/config`) — deliberately minimal for a personal lab, not a cloud bucket. This still demonstrates the real `dvc add`/`dvc push`/`dvc pull` workflow without needing cloud credentials. Swap the remote for S3/GCS/Azure Blob (`dvc remote add -d ... s3://...`) the moment this is used by more than one person.

```bash
dvc pull            # fetch data/sample_metrics.csv from the local remote
dvc add data/sample_metrics.csv   # after regenerating/changing the dataset
dvc push            # publish the new version to the remote
```
